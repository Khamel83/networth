# Bug Fix: "vs Unknown" in Match History

## Problem Statement

**Reported by:** Natalie Coffen
**Symptom:** Player profiles show "VS. Unknown" instead of opponent names in match history

## Root Cause Analysis

### What We Know

1. **Live API Evidence** - The `/api/matches` endpoint returns match data WITHOUT nested player objects:
   ```json
   {
     "player1_id": "fbbed089-...",
     "player2_id": "65ba51ac-...",
     // NO "player1" or "player2" nested objects
   }
   ```

2. **Original Code Used FK Join Syntax:**
   ```python
   # This syntax FAILS silently in Supabase PostgREST
   player1:players!matches_player1_id_fkey(id, name)
   ```

3. **First Fix Attempt Failed:**
   ```python
   # Changed to column name syntax - still fails
   player1:players!player1_id(id, name)
   ```

4. **Why FK Joins Fail (Mystery):** We tried BOTH documented syntaxes:
   - Constraint name syntax: `!matches_player1_id_fkey` - FAILED
   - Column name syntax: `!player1_id` - FAILED
   - Per Supabase docs, column name syntax SHOULD work for disambiguating multiple FKs

5. **Likely Cause:** Our custom `supabase_http.py` wrapper passes the select string as a URL param. PostgREST may handle this differently than the official Supabase client, or there may be URL encoding issues with complex select strings containing `!`, `:`, `(`, `)`.

### Database Schema (from supabase-final-setup.sql)

```sql
CREATE TABLE matches (
    player1_id UUID REFERENCES players(id) ON DELETE SET NULL,
    player2_id UUID REFERENCES players(id) ON DELETE SET NULL,
    ...
);
```

The FK is defined but the constraint NAME is auto-generated by PostgreSQL (not explicitly named).

## Fix Plan

### Approach: Manual Join in Python

Instead of relying on Supabase FK joins (which are fragile and depend on constraint names), fetch players separately and join in Python.

### Files to Modify

1. **api/matches.py** (line 61-67)
   - Fetch matches without FK join
   - Fetch all players into a map
   - Enrich each match with player names

2. **api/profile.py** (function `get_player_matches`)
   - Same approach: fetch matches, then players, then join

### Code Changes Made

#### api/matches.py
```python
# BEFORE (broken FK join)
response = table('matches').select('''
    *,
    player1:players!player1_id(id, name),
    player2:players!player2_id(id, name)
''').order('created_at', desc=True).execute()

# AFTER (manual join)
matches_response = table('matches').select('*').order('created_at', desc=True).execute()
players_response = table('players').select('id, name').execute()
players_map = {p['id']: p for p in players_response.data}
matches = []
for m in matches_response.data:
    p1 = players_map.get(m['player1_id'], {})
    p2 = players_map.get(m['player2_id'], {})
    matches.append({
        **m,
        'player1': {'id': p1.get('id'), 'name': p1.get('name', 'Unknown')},
        'player2': {'id': p2.get('id'), 'name': p2.get('name', 'Unknown')}
    })
```

## Why Manual Join is the RIGHT Solution

1. **Non-fragile:** Doesn't depend on PostgREST FK join syntax which is:
   - Undocumented behavior in edge cases
   - Sensitive to URL encoding
   - Different between Supabase client and raw REST API

2. **Explicit:** The code clearly shows what's happening - fetch matches, fetch players, join them

3. **Performance:** For a small league (~30 players, ~10 matches/month), the performance difference is negligible

4. **Debuggable:** If something goes wrong, you can see exactly where the data came from

5. **Portable:** If we ever switch from Supabase to another database, this pattern works anywhere

## Lessons Learned

1. **Don't trust silent failures:** PostgREST FK joins return empty objects instead of errors when they fail
2. **Verify on live data:** Local tests might pass but production might have different FK names
3. **Explicit is better than magic:** Manual joins are clearer and more reliable than ORM-style FK resolution
